二、发现的问题（按严重度）

严重度问题位置根因 / 影响
P0 跨实例索引失效设计实际不成立
已发布设计在其它实例上“看不见”		 src/lib/catalogVersion.ts:9 版本号用模块级 let version = 0，每个容器实例独立计数。实例 A 发布后 bumpDesignIndex() 只把 A 的版本+1，B/C 仍为 0，其缓存索引（v0）被认为“仍有效”→ 永不重建。注释声称“发布后所有实例一个请求内可见”是错的。后果：新设计在 2/3 实例上对用户不可见，直到该实例冷重启。
P0 每次发布全量 D1 重扫（5.15MB） src/lib/catalogIndex.ts:79 · src/lib/stores.ts:220 getDesignIndex() 每次重建都执行 SELECT data FROM designs（≈5.15MB）+ JSON.parse。由于 P0-1 的失效设计，每次发布只有发布实例重建；但 max_instances=3 下任一实例冷启动也触发。发布频繁或突发冷启动=重复搬运数 MB 数据，拖慢首响。
P1 首页客户端包体携带全量种子目录 src/app/page.tsx:1,6 首页是 "use client" 组件，直接 import { DESIGNS, CATEGORIES, CREATORS, ADAPTERS } from "@/lib/data"。整张种子目录（285 条设计 + 43 SKU 定价表 + 适配器变体）被打进每个访客的 JS 包（连带 pricing.ts 全量成本表）。这是当前最大的客户端体积浪费。修复：把 / 改为 Server Component（数据留在服务端，只下发 HTML）。
P1 探索页 / 列表页仍为 force-dynamic，无边缘缓存 src/app/explore/page.tsx:10 · src/app/listing/[slug]/page.tsx 每次请求直达源站容器（max_instances=3，冷启动敏感），TTFB 受容器冷启动与算力影响。权衡：曾为避开 4.5k slug 的 ISR 磁盘膨胀与改价陈旧而保留 dynamic。更优解：改为按需 ISR——发布时 revalidatePath('/explore') + revalidatePath('/listing/[slug]')，既保新鲜又享边缘缓存。
P1 每请求 O(n) 过滤/排序 + 详情页 O(n) 推荐 src/lib/catalogIndex.ts:130-157, 238-261 publishedPage() 每次请求对 ~4530 项做 filter+sort；relatedFor() 在每次详情页渲染对全量 4530 项做 O(n) 相似度打分。虽注释称“单 digit ms”，但叠加 force-dynamic 后每请求都付此算力，且 relatedFor 结果未缓存。建议：relatedFor 结果按 slug 短期缓存（与索引同生命周期）。
P1 D1 全表扫描、无投影 src/lib/stores.ts:220, 302-303 allPublishedDesigns() 拉 SELECT data FROM designs（整行 JSON blob）；仪表盘 allOrders() 亦 SELECT ... FROM orders 全量扫描。随数据增长线性变慢。建议：索引重建仅取所需列（id/slug/category/creator/tags/price/created_at/palette/shape/adapters）；仪表盘读数加分页/聚合。
P2 Stripe 在支付页顶部急切加载 src/app/checkout/pay/page.tsx:6-21 模块顶部 loadStripe(PUBLISHABLE_KEY) + 同步 <Elements>，会先拉 js.stripe.com/v3 才挂载卡片字段，阻塞支付交互。建议：用 next/dynamic 懒加载 Stripe Elements 包裹层，或在首屏绘制后再加载。
P2 lucide-react 具名导入 ~20 处（DesignCard / SiteHeader / page.tsx 等） 皆用 import { Icon } from "lucide-react"。现代构建可摇树，但图标散落多客户端组件、总量可观。建议：换 lucide-react/dynamic 或按需单图标路径，进一步瘦身初始 chunk。
P2 索引重建无单飞保护（惊群） src/lib/catalogIndex.ts:74-101 冷实例上若多个请求同时到达，各自触发一次 5.15MB 重扫。建议：用 module/promise 单飞（single-flight），首个请求建索引、其余复用。
P2 行为事件每次浏览写 D1 src/app/api/events/route.ts:27 recordDesignEvent 为客户端 beacon 触发、void 异步（不阻塞 TTFB，✓），但 append-only design_events 表随流量持续增长、写量上升。建议：抽样或批量写入，并对表设生命周期/聚合。
P2 边缘预连接/关键资源 preload 缺失 src/app/layout.tsx 字体已自托管（next/font 自动 preload，✓），LCP 为内联 SVG（✓）。但外部依赖（Stripe/GA 门控后）无 preconnect 提示。属低优先级，可在同意后再注入时补 preconnect。

三、根因归类

  • 缓存失效的“共享状态”缺失：版本号、设计索引都是进程内状态，多实例（max_instances=3）下无法协调 → 既导致正确性 Bug（P0-1），也放大数据层成本（P0-2）。这是本次最高优先级的根因。
  • 客户端/服务端边界模糊：首页等本可服务端渲染的页面被标记为 "use client"，把全量种子数据塞进客户端包（P1-1）。
  • 动态优先的惯性：为求“部署即时生效 / 防陈旧”，把营销与探索页一律 force-dynamic，牺牲了边缘缓存这一最大 TTFB 杠杆（P1-2）。应按内容新鲜度分级用 ISR + 按需 revalidate。
  • 查询未做投影/分页：D1 全行拉取（P1-4、P0-2）在数据量增长后成为隐性瓶颈。

四、修复优先级与建议

立即（P0，正确性 + 成本）

  • 将设计索引版本号改存共享存储（D1 单行或 KV），使 bumpDesignIndex 对所有实例可见；或直接改用 revalidateTag('catalog') + revalidatePath，弃用自管内存版本。顺带消除“发布后不可见”Bug。
  • 索引重建加单飞 + 仅取所需列，把 5.15MB 扫描降到最小投影查询。

近期（P1，最大体验杠杆）

  • 把 src/app/page.tsx 改为 Server Component（首页数据不进客户端包）。
  • 探索/列表页改按需 ISR：发布时 revalidatePath，边缘缓存命中、改价即时生效。
  • relatedFor 按 slug 缓存；D1 读数加投影与分页。

优化（P2）

  • 支付页 Stripe Elements 懒加载；lucide 按需导入；consent 后注入脚本补 preconnect；行为事件抽样/批量。
